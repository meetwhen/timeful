## Session Objective

Assess the changes and feasible scope for migrating MongoDB-backed functionality to PostgreSQL. No implementation was requested or started.

## Motivation And Impact

The application currently uses MongoDB directly across backend routes, persistence models, infrastructure, and database-backed tests. A bounded PostgreSQL migration could isolate the currently supported anonymous event-polling flows without rewriting unsupported account and signup features.

## Current State

MongoDB remains the only application database. No source, infrastructure, or configuration files were changed during this session.

## Completed Work

- Mapped MongoDB runtime initialization, collections, models, query paths, deployment/test stack, environment documentation, and historical migration scripts through code inspection.
- Traced anonymous timed and dates-only event creation, loading, mutation, response, and schedule routes.

## Constraints And Assumptions

- The user stated that currently supported creation is limited to anonymously created timed and dates-only events.
- The user stated signup does not currently work; it is not required in a first PostgreSQL slice unless scope changes.
- There is not complete data documentation for the MongoDB models. Any target schema must be inferred from active reads, writes, API transport types, and tests; historical scripts identify legacy data shapes only.
- PostgreSQL and MongoDB may coexist during a phased migration, but all persistent data belonging to one event must have one database authority.

## Findings And Risks

- `server/db/init.go` owns global Mongo client/database/collection handles for `events`, `users`, `dailyuserlogs`, `friendrequests`, `eventResponses`, `attendees`, `folders`, `folderEvents`, and `otpCodes`. Many routes bypass the `server/db/` package and use collections directly.
- Event IDs are Mongo `ObjectID` values exposed as strings. Event lookup uses an 8-character short ID or parses a Mongo ObjectID; frontend dashboard ordering and backend analytics derive creation time from ObjectID timestamps. PostgreSQL-backed events need explicit IDs, `created_at`, and updated resolution/ordering behavior.
- Anonymous event creation uses a nil Mongo owner ID. Normal anonymous timed and dates-only event flows do not require users, folders, attendees, calendar providers, or external calendar integration.
- Guest response ownership uses a local opaque guest ID plus edit token; account response identity uses a Mongo user ID. The current `eventResponses.userId` field overloads account and guest identity and needs an explicit PostgreSQL representation.
- Current ownerless event edits and selected-schedule writes are public. Migrating the storage path without explicitly preserving or changing these rules changes behavior and may retain an authorization issue.
- Groups, folders, authenticated calendar availability, reminders, and response-notification paths depend on Mongo user/account state or external services and are outside a strict anonymous-poll scope.
- Signup responses have a different storage shape from normal responses: they are embedded in `events`, while normal responses are in `eventResponses`.
- Existing multi-collection Mongo writes are not transactional. A PostgreSQL event aggregate should persist event and response/count changes in a single transaction.

## Dependencies And Prerequisites

- Select a PostgreSQL driver/pool and versioned SQL migration tool before implementation. Earlier analysis recommended `pgx/v5` and `goose`.
- Decide whether existing Mongo event data must be imported or whether newly created anonymous polls may begin in PostgreSQL while Mongo remains authoritative for legacy events.
- If both stores coexist, define an unambiguous event source/ID scheme and dispatch reads and mutations to the event's owning repository.
