## Session Objective

The user asked how to speed up the Backend CI job's Docker-heavy steps, suggesting caching specific images.

The intended outcome is a materially faster `backend-quality` job from the ~4m9s baseline (run 33804085825).

The work is in progress: implementation is pushed and measured, but the warm-cache run is not yet faster than baseline because buildx GHA cache I/O became the new bottleneck, and the identified structural fix is not yet implemented.

## Motivation And Impact

Every Backend CI run on a hosted runner re-pulled base images and recompiled all Go code from zero, so contributors waited ~4m9s per backend change and the job had no resilience against slow registry edges (an `npm ci` took 5m in one run versus 10s in the baseline).

The Go compile cache and Docker layer caches did not persist at all between runs before this work.

## Important Decisions

Pre-build images with `docker/build-push-action` (`type=gha`, `mode=max`, `load: true`) and Compose-computed tags instead of compose-bake or registry cache backends.

Left `frontend/e2e/isolated-test-stack.ts` untouched, so its `up -d --build server-test` keeps local semantics while CI's E2E now builds the cheaper `testdeps` target.

Restructured the Dockerfile so the `builder` stage is `FROM testdeps`, deduplicating the module-download layers.

Expanded TASK-0151 scope to include the npm store cache, confirmed by the user.

## Decision Rationale

The default docker-driver BuildKit cannot use the GitHub Actions cache backend and hosted runners are ephemeral, so a docker-container builder via `setup-buildx-action` was required for any cross-run Docker cache.

Tagging images with Compose's computed names lets `compose up`/`compose run` reuse them without workflow flags, and leaving the E2E stack manager unchanged avoided changing local developer behavior.

## Constraints And Assumptions

Test semantics must not change (`-count=1` stays), and `compose.test.yaml` remains the canonical test overlay per AGENTS.md.

Actions are pinned to exact commit SHAs, matching the repo convention from commit fdebd0d4.

Assumption not yet validated: the npm cache makes `npm ci` deterministic on every run (only one warm run observed).

The GHA cache is branch-scoped, so main-branch runs will be cold once until a main run saves caches.

## Findings And Risks

Key finding: `type=gha` image caching is bandwidth-bound for huge module-cache layers — in the warm rerun, the migrator build spent 75.6s in `#16 exporting to GitHub Actions Cache`, and the `testdeps` image's server module-cache layer drives its 88s cost, because `mode=max` re-uploads all layer blobs every run.

Cache I/O, not compilation, is now the bottleneck; the structural fixes are slimming the goose-builder layer with `go clean -cache -modcache` in the same RUN, and optionally moving GOMODCACHE to a second cached volume mounted at `/go/pkg/mod` (requires compose.test.yaml plus the `ensureGoBuildCacheVolume` mirror in frontend/e2e/isolated-test-stack.ts).

The migrator GHA cache missed entirely in run 33853348576 attempt 1 despite a successful export in the prior run; the cause was not verified and may be transient.

The E2E npm slowness (5m for 450 packages) is runner-side registry slowness, unrelated to the Docker changes.

Local developer gotcha: Compose reuses an existing image without detecting a build target change, so after changing a Compose target, run `docker compose build <service>` once.

Concurrency `cancel-in-progress` cancels older runs when new commits land, which cancelled the first warm-rerun attempt.
