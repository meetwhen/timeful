## Implementation Notes

SETTLED DECISION LOG (do not reopen; deviations go to task comments):
- D1 Scope is glossary-only. No prose relinking outside docs/terminology/glossary.md; a follow-up relink pass over the requirements index and titles is deliberately deferred.
- D2 A page-based taxonomy was explicitly chosen over interaction-mode naming. Kind words act as namespace prefixes. One physical route hosts every surface; each entry must say so.
- D3 The planned Timed Event Guest Page was dropped by the owner. The Timed Event Page itself means the main page where all availabilities are visible.
- D4 Owner versus scheduling: only the Event Owner can schedule or edit settings. The Owner Page default is a readable presentation with Edit Event available; during scheduling the page stops being read-only because drawn input sets the Scheduled Event Time. Owner-only scheduling is currently unstated normatively in the FR corpus; see follow-up F1.
- D5 Response Editing Page is where one can potentially edit availability; Response Creation Page is where one can add a response. Prose about editing availability should always name the page it happens on.
- D6 The full five-noun set extends symmetrically to Dates-Only events.
- D7 Availability Editing and Availability Editor are subsumed, not deleted: their headings and anchors stay stable because roughly seven requirement files link them.
- D8 Slot-domain family is exactly Enabled Domain, Active Domain, Inactive Domain, Disabled Domain. The earlier ideas of a Picked-Date Domain entry and an Availability Domain umbrella were dropped on review.
- D9 Inactive Domain may be empty for any event kind; never tie its emptiness to a kind.
- D10 Disabled Domain is bounded to the rendered grid axis (its complement outside rendering is meaningless); relation to existing entries: maps onto Disabled Padding Cells and gray non-picked dates.
- D11 Any standalone coinage named Specific-Times Mode was abandoned. Existing lowercase phrases specific-times page, specific-times mode, and specific-times editing become recorded rejected aliases under the two Scheduling Page entries. Frontend code vocabulary that motivated this lives in frontend/src/composables/event/specificTimesEditDraft.ts and related ScheduleOverlap components.
- D12 State values become subsections under the existing Availability State entry. Canonical value spellings are fixed: the state label is the two-word If needed; If-needed appears only as an adjectival inflection.
- D13 Tier-two additions accepted: Legend, Disabled Status, Dates-Only Grid. Incidental UI labels such as More options, the Responses offcanvas, and Add/Edit availability button styling stay OUT of the glossary.

ENTRY SPECIFICATIONS (definition kernels; executor may tighten wording but not change decided content; one sentence per source line; within-entry references to controlled terms are bolded on first use, matching the file's existing convention):

Event Page Terms preamble fact woven into each entry's first sentence: one physical route renders every listed surface.

1. Timed Event Page - The main page where every availability response of a Timed Event is visible. Umbrella for the owner, scheduling, response editing, and response creation variants below. Authoritative context: FR-002 and FR-064.
2. Dates-Only Event Page - Symmetric main page for a Dates-Only Event. Authoritative context: FR-092 and FR-101.
3. Timed Event Owner Page - The page as seen by an Event Owner: Edit Event is enabled and event settings are editable, in contrast with their read-only presentation to others. Visibility differences are material under Blind Availability. Authoritative context: FR-018, FR-039, FR-084.
4. Dates-Only Event Owner Page - Symmetric variant; timezone settings are owner-restricted here. Authoritative context: FR-018, FR-027.
5. Timed Event Scheduling Page - The owner-only page used to schedule or reschedule an event. Unlike the owner's default reading presentation the page accepts drawn input: dragging sets or clears the Scheduled Event Time directly without painting availability. Records the rejected aliases specific-times page, specific-times mode, and specific-times editing. States the owner-only authority explicitly. Authoritative context: FR-016, FR-085, FR-086.
6. Dates-Only Event Scheduling Page - Symmetric variant whose drawn or selected input is a single scheduled date. Same rejected aliases apply. Authoritative context: FR-012, FR-027.
7. Timed Event Response Editing Page - The page where one can potentially edit an availability response; authority varies with access mode (Protected or Open) and platform identity recovery. Hosts the Availability Editor. Authoritative context: FR-060, FR-061, FR-066.
8. Dates-Only Event Response Editing Page - Symmetric variant for dates-only availability values. Authoritative context: FR-060, FR-061.
9. Timed Event Response Creation Page - The page where one adds a response; saving requires at least one Available or If needed slot. Authoritative context: FR-004.
10. Dates-Only Event Response Creation Page - Symmetric variant; the same non-empty rule guards dates. Authoritative context: FR-004, FR-001.

Domain Terms family (state the invariant once per family, ideally in the Enabled Domain entry: together Active Domain and Inactive Domain constitute the Enabled Domain; Disabled Domain lies entirely outside it):
11. Enabled Domain - Everything generated from Picked Dates: full civil-day slots at the Slot Increment for a Timed Event through the next 00:00 exclusive in the Event Timezone; the picked dates themselves for a Dates-Only Event. Generalizes the timed-event flavor of the existing Enabled Slots entry; say so explicitly. Authoritative context: FR-074, FR-075.
12. Active Domain - The answerable subset of the Enabled Domain: what respondents may record availability on. For Timed Events it coincides with the set of Active Slots and obeys the domain-mode machinery. Authoritative context: FR-016, FR-053.
13. Inactive Domain - The remainder of the Enabled Domain minus the Active Domain. It may be empty for any event kind. Its units coincide with Enabled Inactive Slots. Authoritative context: FR-014.
14. Disabled Domain - Within the rendered grid axis everything outside the Enabled Domain. Its visible representatives are Disabled Padding Cells on timed grids and gray non-picked dates carrying the Disabled status. Authoritative context: FR-014, FR-099.

Timed-slot Terms addition:
15. End-of-Day Boundary - The picker option closing a civil day, labeled 24:00 in 24-hour mode and 12 AM in 12-hour mode; selecting it renders as 00:00 in the next Projected Date Column. Relate it to the Wipe Rule dropping next-day instants beyond the enabled day. Authoritative context: FR-091, FR-015.

Grid Rendering Terms additions (after renaming the section header):
16. Dates-Only Grid - The grid that renders a Dates-Only Event's dates and their availability or scheduling states; counterpart of the Timed Grid. Authoritative context: FR-099, FR-100.
17. Disabled Status - The backticked `Disabled` label and treatment shown when interacting with non-answerable cells, mirroring the timed-grid wording. Authoritative context: FR-099.

Response Access Terms addition:
18. Shared Link - An event-scoped link whose validity gates disclosure of event metadata, respondent names, and availability data. Authoritative context: QR-001, QR-002.

Authentication Terms addition:
19. Event Sign-In - Signing in within an event-page context, associating the Event Visitor Identity and restoring guest access or associating ownership when a valid token is presented; distinct from platform-wide sign-in gated application-wide. Authoritative context: FR-062, FR-063, with FR-007 as the contrasting gate.

UI Elements addition:
20. Legend - The event-page block labeled `Legend` explaining grid and response state colors; remains visible with zero responses and shows only states possible in the current mode, including the If needed item for both event kinds. Authoritative context: FR-009, FR-092, FR-104.

SUBSUMPTION REWRITES (keep headings and anchors byte-identical):

- Availability Editor - Redefine as the editing UI present on those pages while a response is being added or edited; retain FR-005 and FR-066.
