## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
The "What times might work?" one-row layout (NewEvent.vue and NewSignUp.vue, reworked in TASK-0124) needs a fixed, controllable width for each time-range picker and reliable spacing between the 12h/24h format toggle and the range picker on mobile, delivered as one shared component.

Background / root-cause context:
- Both forms duplicate identical start-select + "to" + end-select markup and styles (time-range-row, time-range-select, time-range-separator, time-range-select-item).
- Vuetify's base .v-input rule (display: grid; flex: 1 1 auto) makes selects content-sized whenever a width pin is not applied; today the pin lives in per-file global CSS (.time-range-row .v-input.time-range-select { flex: 0 0 var(--time-range-select-width); width: var(--time-range-select-width); }).
- Mobile width math: card inner width is viewport - 32px (v-card-text uses tw-px-4 below sm). The current row needs ~376px (80px toggle + 2x132px selects + ~16px separator + 2x8px gaps), so on 360px-375px phones justify-between collapses to zero gap and the toggle touches the range picker.

Required outcome:
1. Extract the two range selects + separator into one shared component (proposed: frontend/src/components/TimeRangePicker.vue) used by both NewEvent.vue and NewSignUp.vue, removing the duplicated markup. Active-item highlighting (time-range-select-item--active semantics) is handled inside the component; emits update:start / update:end with return-object option values.
2. Picker width is one component prop (default 132px, hard floor 115px). The prop drives BOTH the chip width (flex: none + fixed width) and menu-props minWidth/maxWidth so chip and menu never diverge. Width must be fixed and independent of content.
3. Keep a single row on mobile (<640px): format toggle left, range picker right, with visible space between them at 375px and 360px viewport widths. Approved tuning levers: time text further left in the chip, dropdown caret (v-field__append-inner) further right, menu item text further left (currently padding: 0 16px), and separator/gap spacing - without truncating values like "09:00" / "9:00 AM". If 115px plus minimal gaps still cannot fit 360px, report back instead of silently violating the 115px floor.
4. Preserve TASK-0124 outcomes: 32px chip height matching TimeFormatToggle, ~40px menu item min-height, and the v-expand-transition collapse behavior when the specific-times switch is on (NewEvent).
5. Coordinate with TASK-0124.01 (vertical centering of label text in the same chips); whichever task lands second must preserve the other's fix.
6. The date-option select in both forms shares the .time-range-select-item class; keep its styling working after the styles move into the component (give it its own class or keep a shared definition).

## Implementation plan (updated 2026-09-01 for user width spec: 100px base growing fluidly to 120px between 420–640px viewports)

1. **New component `frontend/src/components/TimeRangePicker.vue`**
   - Props: `items: TimeFormatOption[]`, `start?: TimeFormatOption`, `end?: TimeFormatOption`, `width?: number` (default 100, hard floor `MIN_PICKER_WIDTH = 100`, growth ceiling `MAX_PICKER_WIDTH = 120`).
   - Emits `update:start` / `update:end` with the selected return-object option.
   - Width expression (one computed, reused everywhere): base = max(width, 100); if base >= 120 → `${base}px`; else `clamp(${base}px, calc(${base}px + (100vw - 420px) * ${120 - base} / 220), 120px)` — pure CSS fluid growth anchored at 420px→640px viewports, no JS viewport detection and no enumerated screen-width branches (the 420/640 anchors are the user-specified growth range).
   - Width handling: inline style `{ width: expr, flex: 'none' }` on each v-select (beats Vuetify's `.v-input { flex: 1 1 auto }`), and `:menu-props="{ minWidth: expr, maxWidth: expr }"` (verified: Vuetify convertToUnit passes CSS strings verbatim to overlay content styles), so chip and menu share one width and never diverge per value ("09:00" vs "11:11").
   - Active highlighting inside the component via `#item` slots (`time-range-select-item--active` when `item.raw.value === start?.value` / `end?.value`).
   - Component owns a global (non-scoped) style block moved out of both forms: 32px chip vars (`--v-field-input-padding-top: 0px; padding-bottom: 4px` kept intact for TASK-0124.01), separator styling, `.time-range-select-item` 40px min-height + semantic active tokens (also styles the date-option select in both forms), plus AC#4 tuning: `--v-field-padding-start: 8px` (chip text further left), menu item padding `0 8px` (text further left), caret spacing verified in browser.
2. **NewEvent.vue / NewSignUp.vue**: replace duplicated select+separator markup with `<TimeRangePicker :items="times" :start="startTimeOption" :end="endTimeOption" @update:start="..." @update:end="..." />`; delete the duplicated `.time-range-*` style rules. Keep `.time-range-row` (toggle left / picker right, justify-between) and add `tw-gap-x-2` so there is a guaranteed minimum gap between toggle and picker (user requirement; prevents zero-gap collapse at 360px).
3. **Unit tests**: new `TimeRangePicker.test.ts` (width default / floor clamp / fluid growth / ceiling, menu-props sync, value-independent width, active highlight via slot-rendering stub, emits). Update `NewEvent.test.ts` / `NewSignUp.test.ts`: render the real TimeRangePicker (`stubs: { TimeRangePicker: false }`) so VSelectStub still sees 3 selects with menuProps; assert the clamp expression; assert row `tw-gap-x-2`; move `.time-range-select-item` style/source assertions to the component source.
4. **Browser verification** (AC#3/#4): measure row fit at 360px/375px and growth at 420px/640px with `npm run inspect -- --target ...`; tune approved levers and verify visible toggle↔picker gap and no truncation of "09:00" / "9:00 AM". If 100px + gaps cannot fit 360px, report back with measurements instead of violating the floor.
