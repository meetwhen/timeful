## Description

# Goal

Push write-path loops and read-modify-write sequences into set-based PostgreSQL statements without schema changes.

# Scope

- `server/postgres/attendees.go:41-59`, `server/routes/postgres_group.go:208-257`, `server/routes/postgres_event_routes.go:1121-1135`: batch attendee account resolution and inserts with `unnest` and `INSERT ... SELECT ... LEFT JOIN LATERAL`, and replace per-email removals with one owner-guarded `DELETE`. Duplicate input emails are tolerated today because each `AddAttendee` call is a separate statement; a set-based `ON CONFLICT DO UPDATE` over duplicates raises PostgreSQL `21000` ("ON CONFLICT DO UPDATE command cannot affect row a second time"), so the batch must dedupe on the exact `(event_id, email)` unique key (case-sensitive) before upserting. Preserve owner protections, decline state, first-occurrence ordering (`WITH ORDINALITY`), and the existing COALESCE identity-fill-on-conflict behavior.
- `server/routes/postgres_group.go:229-239`: the departed-member response cleanup currently does one `GetResponseByPlatformIdentityID` plus `DeleteResponse` per removed member. Replace it with one `DELETE ... RETURNING` scoped by event, `respondent_kind = 'account'`, and the removed platform identities, and decrement `NumResponses` by the returned row count, preserving the owner guard.
- `server/accounts/calendar.go:145-168`: replace the per-sub-calendar upsert, re-read, and per-row delete with one set-based upsert from `unnest` and one `DELETE ... <> ALL(...)`. Resolve the calendar account ID first so a missing account still returns `pgx.ErrNoRows`; a bare `INSERT ... SELECT` plus `DELETE` silently succeeds when the incoming set is empty, and a nil Go slice binds SQL `NULL` so `<> ALL(NULL)` deletes nothing (bind an empty array instead). The batched path avoids `GetCalendarAccountByKey` credential decryption; record that as an intentional behavior change. Keep the Go-side empty-sub-calendar-ID validation that the per-row helper performed, and run through `withTransaction` so `SaveCalendarAccount`'s transaction composes.
- `server/postgres/repository.go:165-179`: keep `UpdateEvent` for settings, schedule, and creation writes, and add targeted repository methods for the response-counter mutations at `server/routes/postgres_event_routes.go:826,854` and `server/routes/postgres_group.go:561,630`. The decrement at `server/routes/postgres_group.go:235` is persisted by the caller's full-row settings write at `server/routes/postgres_event_routes.go:622`; that write persists the group settings payload and must not be replaced by a counter-only update.
- `server/routes/postgres_owner.go:186-204`: set the archive and delete flags with targeted UPDATE statements instead of full-row `UpdateEvent` writes; the `postgresOwnerMutation` row lock and authorization pairing is unchanged.
- `server/postgres/folders.go:93-123`: replace the dynamically assembled SET list with a static `COALESCE` update. Preserve the no-op branch: when both name and color are nil the current code checks existence and returns without bumping `updated_at`, so the static statement needs `updated_at = CASE WHEN $3 IS NULL AND $4 IS NULL THEN updated_at ELSE clock_timestamp() END` (or an explicit existence pre-check). The route cannot express clearing color to `NULL`, so `COALESCE` is semantically equivalent for supplied values.

# Constraints

- Keep the event row lock and transaction boundaries that serialize response mutations.
- Preserve `23505` to duplicate-name error mapping and `pgx.ErrNoRows` not-found behavior, including the calendar sync empty-incoming-set and missing-account cases.
- The batched attendee insert must tolerate duplicate emails, preserve first-occurrence insertion order, and keep the existing owner-removal protection and decline preservation.
- SQL stays in `server/postgres/`.
- No schema changes in this subtask.

- `LockEvent` is owned by TASK-0214.01 and is out of scope here.

## Implementation Notes

Corrected on 2026-09-13 after a code audit of the original scope.

Key corrections:

- `server/routes/postgres_group.go:235` is not an `UpdateEvent` call site; it is the in-memory `NumResponses--` inside `postgresApplyGroupAttendeeEdits`, persisted by the caller's settings write at `server/routes/postgres_event_routes.go:622`. That write also persists the group settings payload, so it is excluded from the targeted-update list.
- `LockEvent` (`server/postgres/identities.go:115-121`) is owned by TASK-0214.01 per that task's corrected scope and notes, and is removed from this subtask's scope and acceptance criteria.
- A set-based `INSERT ... ON CONFLICT DO UPDATE` over duplicate input emails raises PostgreSQL `21000` ("ON CONFLICT DO UPDATE command cannot affect row a second time"), while the current per-row `AddAttendee` calls tolerate duplicates; the batch must dedupe on the exact `(event_id, email)` key.
- A bare calendar `INSERT ... SELECT FROM unnest` plus `DELETE ... <> ALL` silently succeeds when the incoming set is empty and the account is missing, and binds `NULL` for a nil Go slice; the batch must resolve the account first and bind an empty array.
- The folder no-op branch returns without bumping `updated_at`; the static `COALESCE` statement must reproduce that.
- The batched calendar sync avoids `GetCalendarAccountByKey` credential decryption; record during implementation whether that changes expected error behavior.
