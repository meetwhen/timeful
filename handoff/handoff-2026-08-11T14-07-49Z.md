## Detailed Optimization Plan

### 1. Stabilize the Suite Before Measuring Performance

- Keep `getTimedWeekDays()` chronologically ordered so weekly-slot assertions are deterministic.
- Justification: timing comparisons are not credible while a test can fail based on dynamic date ordering.

### 2. Maintain Timing Visibility

- Use `npm run test:unit:profile` when investigating slowdowns.
- Keep `slowTestThreshold: 100` in Vitest so expensive files are visible without separate instrumentation.
- Justification: aggregate Vitest timings identified environment and import costs, but future work needs per-suite attribution.

### 3. Preserve Default Worker Scheduling

- Do not add `maxWorkers` configuration now.
- Benchmarked results: default was 33.78s, 4 workers was 39.95s, and 50% workers was 40.32s.
- Justification: constraining workers is slower on this machine. Re-benchmark on CI before making an environment-specific choice.

### 4. Reduce Unnecessary `happy-dom` Usage

- Audit files with `@vitest-environment happy-dom`.
- Convert only tests that do not mount Vue, depend on browser globals, or exercise DOM behavior to the Node default.
- The first safe conversions are complete:
  - `ScheduleOverlap.breakpoints.test.ts`
  - `useCalendarEvents.test.ts`
  - `useOwnedTimezone.test.ts`
- Justification: 93 files initialize `happy-dom`; environment setup was a major measured cost.

### 5. Target Repeated Heavyweight Mounts

- Profile and refactor `src/views/Event.test.ts`, `src/components/NewEvent.test.ts`, and schedule-overlap grid suites first.
- Move non-rendering state, Temporal, and data-transformation behavior into composable/domain tests.
- Retain a smaller number of component tests for rendered contracts, emitted events, and integration boundaries.
- Reuse existing stubs from `src/test/componentStubs.ts`.
- Justification: these files repeatedly construct Vue wrappers and DOM/reactivity trees, which dominates execution over assertion time.

### 6. Standardize DOM Cleanup Before Sharing Environments

- In DOM suites, unmount wrappers, clear `document.body`, restore timers, and restore mocks in `afterEach`.
- Follow `useTimedGridInteractions.test.ts` as the baseline cleanup pattern.
- Justification: inconsistent teardown risks retained DOM/reactivity state and prevents safely evaluating shared environments.

### 7. Evaluate Lower Isolation Only as a Controlled Follow-Up

- Once cleanup is reliable, benchmark a dedicated DOM project or `isolate: false`.
- Reject it if globals, timers, storage, or mocks leak between files.
- Justification: shared environments may reduce setup overhead but can make the suite flaky, which is worse than the current runtime.

### 8. Keep Full Verification and Improve Local Feedback Separately

- Continue running the full suite in CI and before merge.
- Optionally add changed-file/scoped test workflows for development.
- Justification: faster local loops should not reduce regression coverage.

## Success Criteria

- Full suite remains deterministic and passes.
- Coverage and test isolation are preserved.
- Improvements are accepted only when measured on representative local and CI hardware.
- The next meaningful runtime reduction should come from fewer large Vue/DOM mounts, not worker tuning.
