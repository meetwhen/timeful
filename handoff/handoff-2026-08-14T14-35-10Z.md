## Motivation And Impact

The intended first release moves newly created anonymous timed and dates-only polls to PostgreSQL while retaining MongoDB for existing events and account-backed features. The cut is intended to gain relational constraints and atomic event-response mutations without requiring a full account, calendar, group, folder, signup, or legacy-data migration.

The frontend can remain substantially unchanged only if public event identifiers remain opaque strings, existing Mongo URLs continue to resolve, anonymous ownership behavior is preserved, and event/response transport payloads remain compatible. One small frontend ownership adjustment is expected because PostgreSQL guest edit tokens will be hashed and cannot always be returned after an open edit.

## Important Decisions

- PostgreSQL owns only newly created anonymous timed and dates-only polls in phase one.
- MongoDB retains full read/write authority for all existing events and all account-created events.
- One event aggregate must be wholly authoritative in one database. There will be no dual writes and no event split across MongoDB and PostgreSQL.
- PostgreSQL event IDs use a distinct, route-safe namespace. Unprefixed legacy IDs continue to dispatch to MongoDB.
- The implementation default is a `p_` namespace, with a ULID-based long public ID and a namespaced Crockford-style short ID. The user selected namespaced IDs; the exact suffix lengths remain an implementation detail as long as they are stable and URL-safe.
- Existing Mongo events retain full fallback behavior, including reads and mutations. There is no import-on-read and no read-only legacy mode.
- Account adoption of PostgreSQL-owned anonymous events is deferred. PostgreSQL events remain anonymous after sign-in in phase one.
- Signed-in users may respond as themselves to PostgreSQL-owned anonymous polls. PostgreSQL stores the Mongo user ID as an external string without a cross-database foreign key and retains current Mongo user hydration at the API boundary.
- Existing unauthenticated anonymous event metadata edits remain public.
- Existing selected-schedule save, replace, and clear operations remain public.
- Existing dates-only instant representation, full-civil-day timed slot domain, weekly anchoring behavior, and permissive response-slot behavior are preserved in phase one.
- Anonymous requests using out-of-scope features are rejected explicitly rather than silently falling back to MongoDB or partially persisting data.
- Out-of-scope PostgreSQL features include groups, signup forms, signup blocks/responses, remindees, reminder tasks, notifications, response-threshold emails, blind availability, and email collection.
- The same unsupported-feature restrictions apply when editing a PostgreSQL-owned event, preventing an in-scope event from becoming an unsupported aggregate later.
- Guest edit tokens are hashed with SHA-256 and stored as binary data rather than plaintext.
- A raw guest edit token is returned when a guest response is created.
- A raw token may be returned after a mutation only when the caller supplied and proved possession of that token.
- A tokenless edit of an open guest response returns no `guestCredentials`; it does not disclose or rotate ownership.
- `numResponses` is derived from authoritative PostgreSQL response rows rather than maintained as a separate cached counter in phase one.
- PostgreSQL anonymous-event creation has an independent write feature flag. PostgreSQL reads remain enabled for already-created PostgreSQL events even when new writes are routed back to MongoDB.
- PostgreSQL runs as a production Compose service, not a managed external database.
- All environments use PostgreSQL 18.6 only. The selected image baseline is pinned to `postgres:18.6-bookworm`, not a floating major tag.
- The PostgreSQL driver/pool is `pgx/v5` and the SQL migration tool is Goose.
- SQL migrations run before application startup rather than opportunistically during HTTP startup.
- Once PostgreSQL-owned events can exist, service readiness requires both MongoDB and PostgreSQL because active routes depend on both stores.
- Production receives automated daily compressed PostgreSQL dumps with 14-day retention.
- PostgreSQL backups are written to a configurable host bind mount outside Compose-managed database volumes. Off-host replication of that directory remains an infrastructure responsibility.

## Decision Rationale

- New anonymous polls are the smallest coherent aggregate that can move without rewriting users, authentication, folders, groups, calendars, signup forms, billing, analytics, and historical data.
- Full Mongo fallback preserves existing links and behavior while allowing an incremental rollout.
- Namespaced IDs provide deterministic store dispatch and avoid short-ID races across independent MongoDB and PostgreSQL unique indexes. A shared cross-store locator would broaden every event creation path.
- Preserving transport and authorization behavior minimizes frontend and product changes. Security changes to public event mutation require a separate anonymous-owner credential design and were deliberately deferred.
- Hashing guest tokens removes recoverable bearer credentials from database storage. Not returning credentials after tokenless open edits is necessary because a one-way hash cannot reproduce the original token and rotating it would silently transfer ownership.
- External Mongo user IDs allow current signed-in response behavior without migrating user records or inventing cross-database referential integrity.
- Deriving response counts removes the current Mongo count drift caused by separate event and response writes.
- A write-only rollout flag supports rollback of new creation without making already-created PostgreSQL events inaccessible.
- Pinning PostgreSQL 18.6 avoids surprise binary upgrades and avoids relying on PostgreSQL 19 beta behavior. Minor upgrades will be deliberate and tested.
- Host-mounted dumps survive Compose volume deletion. The database volume itself is not considered a backup.

## Findings And Risks

- `server/routes/events.go` is the primary blast-radius file. It directly accesses Mongo collections throughout the shared public event handlers and has no event service or repository abstraction.
- `server/db/events.go` resolves event sources using Mongo-only rules: identifiers of length at most ten are treated as short IDs and longer values are parsed as ObjectIDs. Namespaced IDs require a deterministic resolver before these rules.
- `server/main.go` initializes, pings, and closes only MongoDB. The health endpoint accepts one database ping, and production `/e/:eventId` metadata lookup is Mongo-only.
- Event and response models combine Mongo persistence types, API transport fields, legacy fields, and derived response maps. PostgreSQL row types should not be forced into `primitive.ObjectID` or BSON omission semantics.
- Mongo ObjectID timestamps currently supply event creation order and duplicate-response recency. PostgreSQL needs explicit `created_at` and `updated_at` values.
- Frontend dashboard sorting derives time from ObjectIDs in `frontend/src/components/home/Dashboard.vue`. It is outside phase one while PostgreSQL events remain anonymous and unadopted, but it blocks future adoption unless an explicit creation timestamp is introduced.
- Guest ownership and pending account adoption are keyed by long event ID in frontend localStorage. Existing IDs cannot be rewritten without a migration of browser state.
- New PostgreSQL IDs must remain path-segment safe. The current loader strips dots and does not consistently URL-encode route identifiers.
- Current Mongo response create/delete operations and `numResponses` updates are separate non-transactional writes. PostgreSQL response row and slot changes must be atomic.
- Current Mongo response uniqueness is application-level and race-prone. PostgreSQL requires event-local unique constraints for account identity, guest ID, and canonical guest name.
- Token-backed guest IDs are 24 hexadecimal characters and can be misclassified as Mongo ObjectIDs during user hydration. A neutral respondent identity model should stop relying on parseability to infer respondent kind for PostgreSQL rows.
- Signed-in respondents create a deliberate cross-store reference. PostgreSQL cannot enforce a foreign key to Mongo users, so user deletion and stale identity behavior must remain compatible and be tested.
- Existing API reads collapse duplicate canonical responses using response ObjectID recency. PostgreSQL constraints should prevent new duplicates and explicit timestamps should define recency where needed.
- The current event update path writes a loaded event struct under `$set`, creating omission and lost-update hazards. A PostgreSQL repository must update explicit columns and child rows rather than emulating BSON omission.
- The current response count can diverge from actual response rows. Derived PostgreSQL counts intentionally correct this behavior and may expose differences if a test expects a stale Mongo count.
- Existing date-only values are semantically ambiguous instants. The PostgreSQL migration preserves ambiguity rather than resolving it, so future civil-date cleanup remains separate work.
- Empty weekly events use the current time as an anchor because no anchor week is persisted. This nondeterminism remains in phase one.
- Current response submissions can contain arbitrary instants not belonging to event dates, active slots, increments, or generated domains. This permissiveness remains in phase one.
- Current anonymous event edits and selected-schedule writes are public. The migration preserves known authorization exposure and must not accidentally imply it was fixed.
- Current blind-availability guest reads can select a response by guest ID/name without an edit token. Blind availability is rejected for PostgreSQL-owned events, but Mongo fallback retains current behavior.
- Current generated Swagger is incomplete for create `shortId`, guest ownership fields, returned guest credentials, and schedule endpoints. Storage-only changes do not require an API break, but touched route annotations should be corrected and regenerated deliberately.
- `frontend/src/composables/schedule_overlap/useAvailabilityData.ts` currently stores guest ownership after every guest mutation, even if the server returns no credentials. Tokenless open edits require a small frontend guard to avoid creating or downgrading local ownership.
- PostgreSQL backups on the same host protect against volume deletion and logical mistakes but not total host loss. Off-host replication remains necessary for host-disaster recovery.
- A PostgreSQL major-version upgrade cannot be performed by only changing the container image because the data directory is not major-version compatible. Future upgrades require `pg_upgrade` or dump/restore.
