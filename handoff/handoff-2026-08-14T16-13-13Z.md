## Important Decisions

### Phase-One Strategy

- Phase one is a compatibility migration, not an identity, authorization, or transport redesign.
- Preserve externally observable current behavior, including awkward behavior, unless a change is technically required to route or persist PostgreSQL-owned events.
- Do not deliberately reproduce internal corruption mechanisms such as ignored SQL errors, non-atomic response/count writes, or race-created duplicate rows. PostgreSQL transactions and constraints may enforce the current intended behavior without changing normal API results.
- Keep the cleaner respondent, response-ownership, normalization, and capability design as explicit future work rather than deleting it from the plan.
- PostgreSQL backup automation, off-host replication, restore drills, RPO, and RTO are deferred future work and do not block enabling PostgreSQL creation in phase one. This supersedes the prior handoff's phase-one backup requirement.

### Store Ownership And Routing

- PostgreSQL owns only newly created eligible anonymous timed and dates-only polls.
- MongoDB remains authoritative for every existing event, authenticated event creation, groups, signup forms, and account-backed features.
- One event aggregate is authoritative in exactly one database. There are no dual writes, import-on-read operations, or split aggregates.
- Existing Mongo long and short IDs retain full read/write fallback behavior.
- The creation-routing flag is named `POSTGRES_ANONYMOUS_EVENT_CREATION_ENABLED`; it affects only the store selected for future creation.
- When the flag is disabled, all anonymous creation uses MongoDB, including shapes unsupported by PostgreSQL. This is a real creation rollback.
- Existing PostgreSQL events remain readable and mutable while new PostgreSQL creation is disabled.
- To minimize product changes, unsupported or noncanonical anonymous creation should continue using MongoDB rather than becoming a new rejection solely because PostgreSQL is enabled. This is the recommended compatibility interpretation of the user's final direction and should be frozen in regression tests before implementation.
- An existing PostgreSQL event cannot move to MongoDB. Attempts to edit it into a feature that its compatibility repository cannot support must return an explicit stable error.
- Account/group-only routes receiving a namespaced PostgreSQL ID should classify the source before Mongo ObjectID parsing. Earlier questioning selected a stable unsupported response rather than accidental parse errors.
- Importing a remote PostgreSQL event into local MongoDB remains unsupported in phase one.

### Public And Internal Identifiers

- PostgreSQL long public event IDs are frozen as `p_` plus a 26-character ULID.
- PostgreSQL short event IDs are frozen as `p_` plus eight Crockford characters.
- The alphabet is restricted to route-safe ASCII letters, digits, and underscore.
- PostgreSQL event API `_id` is always the namespaced long public ID; `shortId` is always the namespaced short ID.
- Both long and short namespaced IDs resolve through `/api/events/:id/ids` and every shared anonymous-poll route.
- PostgreSQL internal event primary keys use UUIDv7 and are not exposed as event API IDs.
- Each PostgreSQL response row also has an internal UUIDv7 primary key.
- PostgreSQL 18's `uuidv7()` should generate internal event and response IDs by database default.
- The future idea of exposing owner-only response UUIDs as part of a new guest capability model is deferred. Phase-one response mutation targeting remains compatible with current guest/account identifiers.

### Current Identity And Guest Behavior To Preserve

- Signed-in respondents continue to be identified externally by their Mongo user ID. PostgreSQL stores that value as an external string without a cross-database foreign key.
- Signed-in callers may still submit as guests.
- Current account-response cardinality and response-map keys remain unchanged in phase one.
- Current token-backed guest IDs remain 24 hexadecimal characters in phase one. The proposed `g_` namespace is future work.
- Current guest response-map keys remain compatible with the frontend and plugin. Do not introduce SQL row IDs or new response keys into phase-one payloads.
- Current guest-name validation remains shared Go boundary behavior: strip control and Unicode format characters, trim, normalize to NFC, enforce a 100-code-point limit, reject ObjectID-like names, and compare normalized names case-sensitively.
- Current guest-name uniqueness behavior remains in phase one. Allowing duplicate display names with ID-only targeting is future work.
- Current one-response-per-account/guest identity behavior remains in phase one. Multiple responses per event-local respondent are future work.
- Current guest edit tokens must remain recoverable in phase one because open tokenless mutation currently returns the stored raw token. Hash-only token storage would require backend and frontend behavior changes.
- Current open-response behavior remains compatible in phase one, including tokenless mutation behavior, returned credentials, policy changes, rename, and deletion. The stricter response-ID/capability rules selected during design exploration are future work.
- Frontend local ownership retains its current long-event-ID-keyed records. The proposed guest record containing multiple response credentials is future work.
- If a Mongo user is deleted after responding, retain the PostgreSQL row and preserve current fallback identity serialization.
- Namespaced PostgreSQL event IDs in `eventsToLink` are skipped by backend ObjectID linking and are discarded from frontend pending adoption after successful sign-in. Account adoption remains deferred.

### API And Product Compatibility

- PostgreSQL anonymous ownership serializes as the existing zero ObjectID sentinel.
- Public anonymous event metadata edits remain available in phase one.
- Public selected-schedule save, replace, and clear remain available in phase one.
- This intentionally preserves behavior that conflicts with accepted frontend ADR-010; the ADR or its status must be updated so it no longer claims anonymous metadata controls must be hidden.
- Plugin `get-slots` and `set-slots` must work for PostgreSQL-owned events with unchanged message payload shapes, response-map semantics, privacy behavior, and guest credential behavior.
- Signed-in responses to PostgreSQL polls remain supported, but those polls do not appear in `/api/user/events` or the dashboard in phase one. This is an explicit compatibility exception selected to avoid expanding account/dashboard scope.
- PostgreSQL anonymous events should contribute to current creator analytics based on `creatorPosthogId`; this was selected before the final blast-radius reduction and remains a contained cross-store read requirement unless explicitly deferred later.
- Remote PostgreSQL events cannot be imported into MongoDB in phase one.
- Public metadata `/e/:eventId` resolution must use the same source classifier as API routes.

### Temporal, Collection, And Schedule Semantics

- API instants remain millisecond values. PostgreSQL must normalize instants to millisecond precision before comparison or serialization.
- Dates-only candidates remain instants rather than SQL civil `date` values.
- Active slots preserve current sorting and deduplication.
- Dates-only candidates, recurrence selected dates, and recurrence selected weekdays preserve input order and duplicates.
- Response availability preserves first-seen order after current deduplication, with `available` winning over `ifNeeded`.
- Response availability remains permissive and is not constrained to event dates, active slots, increments, or generated domains.
- Timed local start/end strings preserve accepted `HH:mm` and `HH:mm:ss` forms verbatim.
- The full-civil-day enabled-slot domain, current weekly anchoring, and empty-week current-time fallback remain unchanged.
- Selected schedules retain current arbitrary-range validation (`end > start` only), epoch-millisecond reads, and snapshot summary behavior. Renaming an event does not update a saved schedule summary.
- The final compatibility direction supersedes the interim choice to make event mode immutable and edits explicit full replacements. Current edit omission, clearing, and conversion behavior should first be captured by tests and matched for PostgreSQL; cleaner replacement semantics are future work.

### PostgreSQL Compatibility Persistence

- The narrow first schema should optimize for behavior parity rather than immediately normalizing every date, recurrence, slot, respondent, response-slot, and schedule concept.
- A compatibility schema using explicit event/response identity columns plus JSONB payloads was recommended because it naturally preserves current omission, order, duplicate, and timestamp-wire behavior while keeping events and responses relationally separate.
- Internal rows must remain separate from HTTP DTOs and Mongo BSON documents. PostgreSQL rows must not be forced into `primitive.ObjectID` fields.
- Event and response mutations should use PostgreSQL transactions.
- A compatibility response count may remain a stored event counter if it is updated atomically with response mutations. Deriving counts and removing the counter is future work.
- The exact compatibility schema has not yet been confirmed in code or an ADR. Freeze route contracts before finalizing its columns.

- Reuse existing storage-independent validation, timed-slot normalization, privacy, identity hydration, and transport behavior where doing so does not force a Mongo model into PostgreSQL persistence.
- Temporary PostgreSQL-specific handler orchestration is acceptable to isolate risk. Consolidation is future work after parity is demonstrated.

## Decision Rationale

- Keeping Mongo handlers unchanged reduces regression risk for every existing event URL and account feature.
- Namespaced public IDs provide deterministic dispatch without a cross-store locator or collision coordination.
- Hidden UUIDv7 primary keys give PostgreSQL-native ordered identities without exposing storage identity through the API.
- Compatibility persistence can still gain atomic response/count mutations and database-enforced intended uniqueness without changing normal route output.
- Preserving raw guest tokens temporarily avoids the otherwise unavoidable behavior change where tokenless open edits can no longer return credentials. Hashing remains the preferred future security design after the frontend and ownership contract change together.
- Keeping current response-map keys avoids changes to signed-in response detection, guest selection, browser storage, and the documented plugin API.
- Deferring event-local respondents, multiple responses, public response keys, and capability handles avoids a broad frontend state and transport migration during the database cutover.
- Routing unsupported anonymous creation to Mongo preserves current product behavior and makes disabling PostgreSQL creation a complete creation rollback.
- A compatibility-oriented schema reduces the number of new tables, joins, ordering columns, serializers, and update semantics that must be proven simultaneously. A later in-PostgreSQL migration can normalize the data after behavior parity is established.
- Backups were explicitly deferred by the user to keep the initial migration focused. This accepts an operational risk that must remain visible rather than being described as completed protection.

## Findings And Risks

- `server/routes/events.go` remains directly coupled to Mongo throughout every shared route. A broad repository refactor would materially increase phase-one risk.
- `server/db/events.go` treats identifiers of length at most ten as short IDs and parses longer identifiers as Mongo ObjectIDs. Namespaced classification must occur before both rules.
- `server/main.go` initializes, pings, closes, and serves metadata through Mongo-only code.
- Current models combine BSON persistence, API transport, legacy fields, and derived data; they cannot directly represent namespaced PostgreSQL `_id` values.
- Current open guest behavior returns plaintext credentials after tokenless mutations. Hash-only storage cannot preserve this behavior.
- Token-backed guest IDs are always 24 hexadecimal characters and can be misclassified as Mongo account IDs by current inference code. The phase-one adapter needs explicit internal respondent kind even if external keys remain compatible.
- Current edit behavior is not a clean partial update or full replacement. BSON `omitempty` makes clearing description, active slots, and mode-specific fields inconsistent.
- Current date candidates and recurrence metadata preserve duplicates and input order, conflicting with the prior handoff's proposed uniqueness constraints.
- The current frontend always sends disabled/default values for unsupported features. Rejecting unsupported field presence would reject normal anonymous creation and editing.
- Credential-less mutation handling is unsafe in both availability submission and rename, but that path is not exercised if phase one preserves current returned credentials.
- Accepted frontend ADR-010 says anonymous metadata controls must be hidden, while current frontend code and tests expose them and the user chose to preserve them.
- The plugin handler is active on every non-group event and exposes response-map keys. Any response identity change is a plugin API change.
- `/api/user/events` is Mongo-only. The selected dashboard exclusion is an intentional phase-one product exception.
- Creator analytics is Mongo-only and derives event time from ObjectIDs. Including PostgreSQL events requires a small cross-store aggregate using explicit `created_at`.
- Remote import unmarshals into `models.Event` and cannot represent namespaced `_id` values. It also derives timed bounds from legacy `Dates` that canonical timed events omit.
- Current Compose and documentation contain unrelated drift; do not copy it into PostgreSQL configuration without review.
- Current route-test Compose command runs only a narrow regex and omits relevant timed payload and schedule tests.
- `go test ./...` is unsafe and non-hermetic until the Microsoft Graph live test credential is revoked and the test is mocked.
- Production status of the canonical timed-event, short-ID unique-index, and canonical respondent-name Mongo migrations is not recorded.
- Deferring PostgreSQL backups means PostgreSQL-owned polls have no repository-provided recovery mechanism in phase one. This is accepted but must be documented before rollout.
